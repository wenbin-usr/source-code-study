## 1. 高可用设计总览

### 1.1 三层故障域划分

Pulsar 的 HA 不是单一机制，而是**三层各自独立容错、互相配合**的体系。存算分离是根基：broker 不持有数据，因此 broker 故障的恢复是"元数据锁失效 + 重新打开 ledger"的**秒级逻辑接管**，而非数据搬迁。

| 层 | 故障对象 | HA 机制 | 数据丢失风险 | 典型恢复时间 |
|---|---|---|---|---|
| 存储层 | Bookie 宕机 / 磁盘故障 | E/W/A Quorum 多副本 + 放置策略 + AutoRecovery 补副本 | W-1 台同时宕机以内不丢 | 写入即时无感；副本修复分钟级 |
| 服务层 | Broker 宕机 / 网络分区 | bundle 临时锁失效 → 其他 broker 接管 + ledger fencing 防脑裂 | 不丢（已 ack 的都在 BK） | 会话超时（默认 30s）+ topic 懒加载 |
| 元数据层 | ZK/Oxia 会话断开 | 会话监控、锁重验证、`reconnect`/`shutdown` 策略 | 不丢（元数据本身多副本） | 自动重连，断开超过 sessionTimeout×5/6 判定 SessionLost |
| 客户端 | 与 broker 断连 | 重连引擎 + epoch 防旧 + 消息重发 + 消费重投 | 生产侧依赖重发语义 | Backoff 退避重连，通常亚秒到秒级 |
| 跨集群 | 远端集群整体故障 | Replicator 退避堆积 + TTL DISCARD 丢弃 | 复制语义内可控 | 远端恢复后自动续传 |

### 1.3 一句话总结各层原理

- **存储层**：每条消息写 E 台、等 W 台确认即成功；任一 bookie 挂掉，quorum 写入继续；后台 AutoRecovery 把副本数补回 E。
- **服务层**：broker 对 bundle 的所有权是元数据存储里的**临时节点**；会话一断锁自动消失，其他 broker 可立即创建锁接管；接管者以 recovery 模式打开 ledger，**fence 掉旧 broker 的写入权**，杜绝脑裂双写。
- **元数据层**：ZK/Oxia 自身是多数派集群；上层用会话事件驱动锁重验证与 leader 重选举。
- **客户端**：断连后按 Backoff 重连，重连成功后重握手、重发未确认消息、重投未 ack 消息；epoch 机制保证旧连接的迟到响应不会污染新连接状态。
- **跨集群**：复制本质是一个特殊的 producer，远端故障时退避重连、本地 backlog 堆积，超过 TTL 可按 DISCARD 策略丢弃。

## 2. 存储层高可用 —— BookKeeper 多副本

### 2.1 E/W/A Quorum 写入模型

每个 ledger 条目写入时，BookKeeper 客户端从 ensemble（E 台 bookie）中选出 quorum 写入：

- **Ensemble size (E)**：一个 ledger 的条目分布到的 bookie 总数（条目以 round-robin 落在 E 台中连续 W 台上）；
- **Write quorum (W)**：每条消息实际复制的份数；
- **Ack quorum (A)**：收到 A 台确认即向生产者返回成功。

**可用性公式**：只要 ensemble 中有 ≥ W 台 - (W - A) … 更准确地表述——写入可用需要"连续 W 台中至少 A 台存活"；读取可用需要 LAC 之后的数据至少 A 台存活。默认 `2/2/2` 意味着**允许 1 台 bookie 故障不丢数据、不影响写**（W-A = 2-2 = 0 冗余 ack，E-W = 0 冗余放置，但任一台挂掉时写入会切换到新的 ensemble 组合）。

```mermaid

    autonumber
    participant ML as ManagedLedgerImpl
    participant BKC as BookKeeper 客户端
    participant BK1 as Bookie-1
    participant BK2 as Bookie-2
    participant BK3 as Bookie-3

    ML->>BKC: asyncAddEntry(entry)
    BKC->>BK1: 写 entry (E=3, W=2, A=2)
    BKC->>BK2: 写 entry
    BKC->>BK3: 写 entry

    BKC-->>ML: addComplete(ledgerId, entryId)
    Note over ML: 此时 BK2 即使宕机也不影响该条目
```

Broker 侧 BK 客户端配置集中在 `pulsar-broker/src/main/java/org/apache/pulsar/broker/BookKeeperClientFactoryImpl.java`：

- `createBkClientConfiguration()`（L104）：集中构建 `ClientConfiguration`；
- 放置策略注册（L176）：按配置装载 `RackawareEnsemblePlacementPolicy` / `RegionAwareEnsemblePlacementPolicy` / 自定义策略；
- bookie 健康检查（L148-156）：`enableBookieHealthCheck` + `bookieHealthCheckIntervalSeconds` 等， unhealthy bookie 会被临时从 ensemble 选择中剔除（quarantine）；
- speculative read（L132）：读超时后向另一台 bookie 发起投机读，降低尾延迟与单点读故障影响；
- **`bookkeeper_` 前缀透传**（L165-172）：Pulsar 配置文件里任何 `bookkeeper_xxx=y` 都会原样传给 BK 客户端，无需为每个 BK 参数单独立配置键——这是排查存储层参数时的重要入口。

### 2.2 副本放置策略

放置策略决定 ensemble 选哪些 bookie，直接决定故障域的隔离能力：

| 策略 | 类 | 行为 |
|---|---|---|
| 机架感知（默认） | `org.apache.bookkeeper.client.RackawareEnsemblePlacementPolicy` | 尽量把同一 ledger 的副本分散到不同 rack/zones，单机架故障不丢 ledger |
| 区域感知 | `org.apache.bookkeeper.client.RegionAwareEnsemblePlacementPolicy` | 跨 region（如 dc-1/dc-2）放置，minRacksPerWriteQuorum 控制每个写 quorum 的最小机架数 |
| 隔离组 | `pulsar-broker-common/src/main/java/org/apache/pulsar/bookie/rackawareness/IsolatedBookieEnsemblePlacementPolicy` | 按 namespace 维度把指定 topic 的 ledger 限制在特定 bookie 组内 |

隔离组策略的三个核心方法（均为源码验证）：

- `newEnsemble()`（`IsolatedBookieEnsemblePlacementPolicy.java` L134）：从允许的隔离组中挑 ensemble，若组内 bookie 不足直接失败（不偷偷借用组外 bookie）；
- `replaceBookie()`（L145）：替换故障 bookie 时同样只在组内选；
- `getExcludedBookiesWithIsolationGroups()`（L220）：计算被隔离策略排除的 bookie 集合——**特殊值 `"*"` 组用于系统 topic**（如 `__change_events`），保证系统 topic 的流量与业务 topic 隔离。

### 2.3 Bookie 故障检测与健康检查

两层检测协同：

1. **客户端层（broker 内的 BK 客户端）**：写失败触发 bookie 标记，`replaceBookie()` 在当前 ledger 内即时换一台 bookie 写后续条目，**正在写的 ledger 不中断**；健康检查（L148-156 配置）周期性探活，连续失败的 bookie 进入 quarantine 状态一段时间。
2. **服务端层（AutoRecovery）**：见 2.6。

### 2.4 Ledger Fencing —— 脑裂防护核心

存算分离下最危险的场景：旧 broker 网络分区后"诈尸"，仍认为自己拥有 topic 并继续写 ledger。BookKeeper 用 **fencing** 一票否决：

- **recovery 模式打开 ledger**：`open(ledgerId, recovery=true)` 会向 ensemble 中**所有** bookie 发起 fence 请求（写 fence 标记），旧 writer 再写任何 bookie 都会收到 `LedgerFencedException`；
- 这是最终一致性裁决：即使旧 broker 还活着，它的写也会失败。

### 2.5 Broker 崩溃后打开 ledger 的恢复流程

接管 broker 加载 topic时（`ManagedLedgerImpl.asyncOpenLedger`，`managed-ledger/src/main/java/org/apache/bookkeeper/mledger/impl/ManagedLedgerImpl.java` L511，`recovery=true`）：

恢复后旧 broker 的写失败路径（`ManagedLedgerImpl`）：

- `addEntryFailedDueToConcurrentlyModified()`（L1908）：写 ledger 因被他人 recovery 打开而失败时的统一入口；
- 状态机置 `State.Fenced`（State 枚举 L288；`setFenced()` L4505）——此后该 broker 上此 ML 的**所有写请求直接失败**，并触发 topic 层面向客户端发 `TopicMigrated`/断连，让客户端去新 owner；
- 写超时兜底：`scheduleAddEntryTimeoutTask()`（L4741）+ `OpAddEntry.handleAddFailure()`（`OpAddEntry.java` L361）/ `addComplete` 的超时检查（L240），防止 bookie 半死不活导致写永久挂起；
- 游标持久化遇到不可恢复 BK 错误时：`ManagedCursorImpl.isBkErrorNotRecoverable()`（L3863）判断错误类别，决定重试还是放弃该游标状态。

### 2.6 AutoRecovery —— Auditor / ReplicationWorker / DeathWatcher

Pulsar 发行版把 BookKeeper 的自动恢复进程内置了（`pulsar-broker/src/main/java/org/apache/pulsar/PulsarBrokerStarter.java`）：

- `bin/pulsar bookie` → `-rb` 启动 bookie（L249：`org.apache.bookkeeper.server.Main`）；
- `bin/pulsar autorecovery` → `-ra` 启动自动恢复守护进程（L258：`org.apache.bookkeeper.replication.AutoRecoveryMain`）。

AutoRecoveryMain 内部三个组件：

```mermaid
flowchart TB
    subgraph AR["AutoRecoveryMain (独立进程)"]
        AUD["Auditor<br/>周期扫描全部 ledger<br/>找出副本数不足 (under-replicated)"]
        RW["ReplicationWorker<br/>对 under-replicated ledger<br/>执行 rereplication: 读出数据→写新 bookie→删旧"]
        DW["DeathWatcher<br/>watch /ledgers/available<br/>bookie 下线即时通知 Auditor 提前扫描"]
    end
    subgraph ZK
        LEDGERS["/ledgers/available/...<br/>bookie 存活节点"]
        UR["underreplicated 标记"]
    end
    DW -->|"watch"| LEDGERS
    DW -->|"bookie 死亡"| AUD
    AUD -->|"标记"| UR
    RW -->|"消费"| UR
    RW -->|"复制副本"| Bookies["Bookie 集群"]
```

关键语义：

- **写路径不等恢复**：bookie 挂掉的瞬间，正在写的 ledger 由 `replaceBookie()` 即时换机，已有 ledger 的副本修复由 ReplicationWorker 异步补——写入可用性与副本完整性解耦；
- **under-replicated ledger 仍可读写**：只要剩余副本满足读 quorum，业务无感；
- Auditor 由 AutoRecovery 集群内部选举执行（避免多实例重复扫描），因此 autorecovery 可以部署多个实例实现自身 HA。

## 3. 服务层高可用 —— Broker 无状态接管

### 3.1 Bundle 所有权：临时锁机制

broker 对 bundle 的所有权 = 元数据存储中的一个**临时节点（ephemeral node）**，路径形如 `/namespace/<tenant>/<cluster>/<namespace>/<start>_<end>`，值为 `NamespaceEphemeralData`（`pulsar-broker/src/main/java/org/apache/pulsar/broker/namespace/NamespaceEphemeralData.java`）：

| 字段 | 含义 |
|---|---|
| `brokerId` | 持有者唯一标识 |
| `nativeUrl` / `nativeUrlTls` | 二进制协议服务地址（客户端重定向目标） |
| `httpUrl` / `httpUrlTls` | 管理接口地址 |
| `disabled` | 是否禁用（优雅关闭期间置位，告知他人本 broker 即将退出） |
| `advertisedListeners` | 多 listener 地址表 |

获取链路（`OwnershipCache.tryAcquiringOwnership()`，`OwnershipCache.java` L275）：

```mermaid
sequenceDiagram

    participant NS as NamespaceService

```

要点（`OwnershipCache.java` / `ResourceLockImpl.java`，均在 L107-176 / L151 附近）：

1. 锁本质是 `store.put(path, payload, Optional.of(-1L), EnumSet.of(CreateOption.Ephemeral))`——**version=-1 即"不存在才创建"的 CAS**，加上 Ephemeral 标志，会话一断节点自动消失；
2. `LockBusyException` 说明有人在写（可能是自己也可能是别人），走 `revalidate()` 分辨；
3. 所有成功获取的锁登记进 `locallyAcquiredLocks`（L113），broker 关闭时统一释放。

### 3.2 OwnershipCache 与代数（generation）安全

接管过程中最容易出现"旧代回调污染新代状态"的竞态。OwnershipCache 用**代数比对**防御：

- 每个 `OwnedBundle` 包装**一次特定代**的 `ResourceLock`；
- 锁过期回调（L115-158）触发时：先从 `locallyAcquiredLocks` 移除该锁（带代数检查）；再判断缓存里当前的 `OwnedBundle` 是否还是触发的这一个（L137 `getOwnedBundle(namespaceBundle) == ownedBundle`），**只有相同才执行** `namespaceService.unloadNamespaceBundle()`；
- `removeOwnership(OwnedBundle)`（L380）同样只在锁对象匹配时才释放；
- `bundleOperationBarriers`（L93）把对同一 bundle 的获取/释放操作串行化；
- 发布竞态兜底（L159-173）：若 `OwnedBundle` 在放入缓存前锁就已过期，直接 `IllegalStateException("Lock for bundle ... expired before ownership could be published")`，加载失败而非带病上线。

### 3.4 元数据会话失效：ZKSessionWatcher 与会话策略

`pulsar-metadata` 模块的会话监控链（ZK 实现）：

- `ZKMetadataStore`（L110）创建 `ZKSessionWatcher`：单线程调度器以 `ticktimeMillis = sessionTimeout / 15`（30s 超时即每 2s）用 `zk.exists("/")` 探活；
- **判定 SessionLost 的两个条件**（`ZKSessionWatcher.java`）：
  1. Disconnected 持续超过 `monitorTimeoutMillis = sessionTimeout × 5/6`（30s 超时即 25s）——这是"ZK 还没报 Expired 但实际已经凉了"的主动兜底；
  2. ZK 主动上报 `Expired` 事件——立即判定；
- 重连成功（SyncConnected）：若此前已 SessionLost，补发 `Reconnected + SessionReestablished` 两个事件，否则只发 `Reconnected`；
- `ZKMetadataStore.receivedSessionEvent()`（L159）：收到 `SessionReestablished` 时**先重建 `/` 上的持久递归 watch**（`AddWatchMode.PERSISTENT_RECURSIVE`），再通知监听者——保证后续通知不丢；若 watch 重建失败，强制使会话过期重来。

Broker 对 SessionLost 的响应（`PulsarService.handleMetadataSessionEvent()`，L1280，注册于 L933）：

```java
private void handleMetadataSessionEvent(SessionEvent e) {
    if (e == SessionEvent.SessionLost
            && config.getZookeeperSessionExpiredPolicy() == MetadataSessionExpiredPolicy.shutdown) {
        shutdownNow();
    }
}
```

```mermaid
flowchart TD
    SE["SessionEvent.SessionLost"] --> P{zookeeperSessionExpiredPolicy}
    P -->|"reconnect (默认)"| RC["保持运行<br/>等待会话重建<br/>锁由 LockManagerImpl 自动重验证"]
    P -->|"shutdown"| SN["shutdownNow() (L2360)<br/>closeMetadataServiceSession()<br/>→ 主动关闭会话，释放全部临时锁<br/>→ processTerminator.accept(-1) 进程退出"]
    RC --> RE["SessionReestablished<br/>ResourceLock/LeaderElection 重验证<br/>MetadataCache 先重建 watch 再恢复"]
```

两种策略的取舍：

- **`reconnect`（默认）**：适合 ZK 短暂抖动多的环境；代价是抖动期间（最长 sessionTimeout+ 侦察期）本 broker 的 bundle 锁处于"可能已被删"的悬空态，依赖锁过期回调 + 客户端 lookup 兜底，**存在短暂双主窗口**，最终由 ledger fencing 兜住正确性；
- **`shutdown`**：SessionLost 即自杀，锁立刻消失，接管最快、无双主窗口；代价是对 ZK 抖动零容忍，broker 频繁重启。

### 4.1 元数据存储实现与 SPI

### 4.2 ZK 会话监控与重连（元数据层细节）

### 4.5 MetadataCache 跨 broker 推送失效

## 5. 客户端故障转移

### 5.1 重连引擎 ConnectionHandler

`pulsar-client/src/main/java/org/apache/pulsar/client/impl/ConnectionHandler.java` 是 Producer/Consumer 共用的重连状态机：

| 方法 | 行号 | 职责 |
|---|---|---|
| `grabCnx()` | L99 | 从 ConnectionPool 拿/建连接并发起握手 |
| `reconnectLater()` | L194 | 按 Backoff 延迟后重试 grabCnx |
| `connectionClosed()` | L227 | 连接断开的统一入口（无论主动被动） |
| `isValidStateForReconnection()` | L283 | 判断当前状态是否还允许重连（已关闭则不重连） |

**Backoff 退避**：初始间隔 ×2 指数增长，封顶 `maxBackoffIntervalSec`，**加抖动（jitter）**避免大量客户端同频重连风暴，且带 `mandatoryStop`（ProducerImpl L350 附近配置）——退避曲线不会越过最大 deadline，保证 sendTimeout 语义可预期。

**epoch 防旧机制**（L52-55 / L277-280）：每次 `connectionClosed` 后 `epoch++`；握手回调携带发起时的 epoch，与当前值不符说明期间又断过一次，**直接丢弃这次过期回调**：

```java
// ProducerImpl.recoverProcessOpSendMsgFrom (L2858) 的守护条件
if (expectedEpoch != this.connectionHandler.getEpoch() || cnx() == null) return;
```

这防止"重连竞态下旧连接的 CONNECTED/ERROR 响应覆盖新连接状态"。

`ClientCnx.channelInactive()`（L518-560）是连接级断开的分发中枢：遍历挂在该连接上的所有 producer/consumer 请求 future，逐个以异常完成并触发各自 `connectionClosed` → 重连流程。

### 5.2 Producer failover

重连成功后 `ProducerImpl.connectionOpened()`（L2108-2319）做的远不止重新握手：

1. 重发 `CommandProducer`（带 `ProducerAccessMode` 与**递增 epoch**，见下）；
2. 恢复 chunking 状态、重置背压（信号量 + MemoryLimitController）；
3. **`resendMessages()`**（L2393-2427）：把 pending 队列中未确认的消息全部重发——这是"客户端/broker/存储"三方都可能丢消息时恢复一致性的关键（消息在收到 broker ack 前永远留在客户端内存）。

**Producer fencing（服务端配合）**：`ProducerAccessMode`（Exclusive / WaitForExclusive / Shared）下，新 producer 以更高 epoch 抢占注册时，旧 producer 后续写会被 broker 拒绝并回 `ProducerFencedException`，客户端据此永久关闭自己——与 BK ledger fencing（2.4）同构，防止双 producer 双写。

**sendTimeout 兜底**（L2491）：超时任务周期扫描 pending 消息，超过 `sendTimeoutMs`（默认 30s）的以 timeout 异常失败并放行背压——防止故障期间背压永久卡死。

### 5.3 Consumer failover

`ConsumerImpl`（`pulsar-client/src/main/java/org/apache/pulsar/client/impl/ConsumerImpl.java`）：

- `connectionOpened()`（L878-1066）：重发 `CommandSubscribe`（带递增 **consumerEpoch**——failover 订阅下防旧 consumer 抢占）+ `CommandFlow` 补发 permit；若连接的是新 owner broker，服务端 Dispatcher 重建；
- `connectionFailed()`（L1133-1161）：按重试类型决定是否需要重新 lookup（broker 重启/迁移后地址可能已变）；
- `redeliverUnacknowledgedMessages()`（L2232-2290）：**断连时未 ack 消息全部要求重投**——at-least-once 语义的来源（Shared 订阅请求 broker 重发；Failover 由新 active consumer 自然重收）；
- `activeConsumerChanged()`（L1271-1283）：处理服务端 `ACTIVE_CONSUMER_CHANGE` 命令——failover 订阅的 active 角色变化回调（服务端触发方 `ClientCnx.handleActiveConsumerChange` L922-930）；
- `handleCloseConsumer`（`ClientCnx` L1291-1312）：broker 主动关闭（卸载/迁移）时携带新 broker URL，客户端直连过去；
- **ZeroQueueConsumerImpl 的防旧特化**（`consumerIsReconnectedToBroker` L140-149 + stale guard L114-123）：零队列（Reader）模式在重连瞬间必须丢弃旧连接上仍在飞的 MESSAGE 推送，否则会乱序/重复投递给用户回调。

### 5.4 Lookup 重试、重定向与 TOPIC_MIGRATED

- **重定向跟随**：`LOOKUP_RESPONSE` 返回 redirect 时客户端自动向目标 broker 再查，上限 `maxLookupRedirects=20` 防环；
- **重查找**：连接断开且怀疑 topic 已迁移时（`connectionFailed`），重新执行完整 lookup 流程而非盲目重连原地址——broker 接管后物理地址已变；
- **TOPIC_MIGRATED**（`ClientCnx.handleTopicMigrated` L1105-1130）：broker 明确告知"topic 已迁到集群 X 的 broker"，客户端直连命令携带的 `brokerUrl`，跳过 lookup，收敛更快（配合 3.8）。

### 5.5 服务地址隔离与自愈

`PulsarServiceNameResolver`（`pulsar-client/.../impl/PulsarServiceNameResolver.java`）对 serviceUrl 列表做可用性管理：

- `resolveHost()`（L71-93）：**轮询**而非随机选择地址，故障后流量自动摊到下一台；
- `markHostAvailability()`（L167-211）：连接成功/失败反馈给 resolver；连续失败的地址进入 **quarantine（隔离）**，临时从轮询池摘除；隔离有 TTL，到期自动放回重试——**故障地址自愈**，无需人工干预（Proxy 地址列表、多 serviceUrl 集群地址都受益）。

### 5.6 事务客户端重连

事务场景的 `TransactionCoordinatorClient` 依赖各 TC 分区的 leader 位置：客户端订阅 assignment 变更通知（见 9.3），TC leader 变化后自动重连新 leader——`newTxn`/`addPublishToTxn`/`endTxn` 请求失败时按 epoch/assignment 重试。

## 6. 跨集群容灾 —— Geo-Replication

复制的本质：本地 broker 为每个远端集群起一个**内部 producer**（Replicator），把本地 topic 的消息转发到远端。因此"远端集群故障"退化为"内部 producer 目标不可达"问题。

### 6.1 复制器退避与断连

`AbstractReplicator.startProducer()`（L192-247）与 `PersistentReplicator`：

- producer 断连后进入 `Disconnected` 状态，按 Backoff 退避重连，**消息继续写入本地 ledger，仅复制游标暂停**——本地生产不受任何影响；
- `readFailureBackoff`（`PersistentReplicator.java` L104-107）：读本地 backlog 失败时的退避；
- `disconnectIfNoTrafficAndBacklog()`（L275-297）：远端长期无流量且无积压时主动断开 producer 省资源，有新消息再重连。

### 6.2 远端不可达时的 backlog 与 TTL DISCARD

远端故障期间，复制游标（本质是一个名为 `pulsar.repl.<remote-cluster>` 的订阅）停在原地，本地 backlog 无限增长。两道防线（`PersistentReplicator.java`）：

- `readEntriesFailed()`（L580-616）：读本地 entry 失败（常见于 ledger 被 trim 掉了——积压太久）时按错误类型决定重试或跳过；
- **TTL 丢弃**（L786-801）：消息超过 TTL 后，即使复制游标未消费，也允许按 backlog quota 的 `DISCARD` 策略释放——即**接受"远端故障超过 TTL 的消息不再复制"**，用一致性换可用性；`MINIMUM_BACKLOG_FOR_EXPIRY_CHECK = 1000`（L111）：积压低于 1000 条时不做过期检查，省 CPU。

```mermaid
flowchart TD
    RD["远端集群不可达"] --> DISC["Replicator → Disconnected<br/>Backoff 重连"]
    DISC --> BK["本地写入照常<br/>复制游标停住 → backlog 增长"]
    BK --> Q{backlog 超限?}
    Q -->|"否"| WAIT["等待远端恢复<br/>恢复后从游标续传"]
    Q -->|"是 + TTL/DISCARD 策略"| DROP["按策略丢弃过期消息<br/>（显式接受复制缺口）"]
    RD -.->|"恢复"| RESUME["重连成功 → 从游标继续复制"]
```

### 6.3 双活语义

两个集群互配 replication 即双活：双向各有一个 Replicator；配合 `configurationMetadataStore`（4.3）共享全局命名空间元数据。集群级故障（整机房）靠**异步复制 + TTL 策略**在 RPO（允许丢多少）与资源占用间取舍。

## 7. Proxy 层高可用

Proxy 自身**完全无状态**（不持有 topic/锁），HA = 水平扩容 + 客户端重连：

- **服务发现**：`BrokerDiscoveryProvider.nextBroker()`（`BrokerDiscoveryProvider.java` L86-96）从 broker 注册列表**轮询**选一台做 lookup/直连目标——broker 挂掉后注册消失，轮询自动绕开；
- **后端失效**：`DirectProxyHandler.ProxyBackendHandler.channelInactive`（L550-552）后端连接断开时**立即关闭入站（客户端）连接**——不做故障转移伪装，而是让客户端走自己的完整重连 + 重 lookup 流程（5.x），由元数据层的最新所有权信息决定新目标，避免 proxy 持有过期拓扑；
- **Lookup 代理**：`LookupProxyHandler.performLookup`（L144-209）跟随 broker 重定向（同样受客户端 `maxLookupRedirects` 约束的层级）；
- **部署**：客户端 serviceUrl 指向 proxy 集群的多个地址，配合 5.5 的地址隔离自愈。

## 9. 特殊 Topic 的 HA 语义

### 9.1 非持久化 Topic：显式的可用性换可靠性

`NonPersistentTopic.publishMessage()`（`NonPersistentTopic.java` L200-233）的语义与持久化完全不同：

```java
public void publishMessage(ByteBuf data, PublishContext callback) {
    // ... size check
    callback.completed(null, 0L, 0L);   // ← 先 ack 生产者！
    // 再分发到各订阅 dispatcher / replicator（纯内存）
}
```

- **无 BK 写入、无游标、订阅纯内存**；broker 宕机时在途消息全部丢失、订阅重建；
- epoch 仅内存（`incrementTopicEpoch()` L235 / `setTopicEpoch()` L241），无 fencing 持久化裁决；
- 无去重、不支持事务（直接 `UnsupportedOperationException`）；
- 结论：**非持久化 topic 的 HA 仅到"broker 接管后恢复服务"级别，不保证消息不丢**——选型时必须明确。

### 9.2 系统 Topic

`__change_events`、`__transaction_coordinator_assign`、`__bundles` 等系统 topic 是**持久化 topic**，走标准 bundle 接管 + ledger 恢复，数据在 BK，无特判；隔离组策略可用 `"*"` 组把系统 topic 流量隔离到专门 bookie（2.2）。

### 9.3 事务协调者（TC）failover

两代实现：

- **旧代**（`TransactionMetadataStoreService`）：TC 分配绑定 `transaction_coordinator_assign` 系统 topic 所在 bundle 的所有权——bundle 接管（3.3）即 TC failover，元数据在系统 topic 里，不丢；
- **新代 TransactionCoordinatorV5**（`pulsar-broker/.../transaction/coordinator/v5/TransactionCoordinatorV5.java`，`transactionCoordinatorScalableTopicsEnabled` 开启）：**元数据驱动 elect-all**——
  - 每个 broker 对**每个** TC 分区 N 都在 `/txn/tc/leader/<N>` 上参与选举（L74-79），N 个独立选举，天然均衡；
  - 客户端经 `WATCH_TC_ASSIGNMENTS` 命令拉取全量 assignment 快照（`buildAssignmentsSnapshot()` L329），并注册变更监听（`registerAssignmentChangeListener` L352，`CopyOnWriteArrayList`，变更即触发重连新 leader）；
  - leader 宕机 → 临时节点消失 → 其他 broker 重跑 `elect()` 接管；TC 状态存元数据存储（`TxnMetadataStore`），**接管无状态**；
  - 超时/GC 扫描仅由分区 0 的 leader 执行，避免重复扫描。
